# 추천 시스템 대시보드 전달 문서 (담당자용)

## 1) 문서 목적
이 문서는 현재 구현된 대시보드의 전체 구성(화면/로직/지표)과, 보고서 필수 항목인 공식·가중치 근거를 한 번에 전달하기 위한 문서입니다.

## 2) 현재 대시보드 구현 범위
- UI 스택: FastAPI + 정적 프론트엔드(HTML/CSS/JS)
- 메인 화면 탭:
1. 파이프라인 프로세스
2. 버전별 업그레이드
- 데이터 소스:
1. 파이프라인/해석: 서버 내 상수(`PIPELINE_STAGES`, `PIPELINE_FLOW`, `TRANSITION_NOTES`, `VERSION_NOTES`)
2. 지표: `data/eval_report_v*.json`

## 3) 탭 1: 파이프라인 프로세스 (현재 구현 내용 전체)

### 3-1. 프로세스 단계(총 10단계)
| 단계 | 라벨 | 핵심 역할 |
|---|---|---|
| 1 | 질의 입력 | 사용자 자연어 질의와 옵션(top_k) 수집 |
| 2 | 질의 정규화/파싱 | 선호/제외/필수/소프트 취향 추출 |
| 3 | 질의 유형 분기 | 일반 질의 vs `~같은 게임` 질의 분리 |
| 4-A | 일반 질의 경로 | 참조 게임 없이 일반 검색 경로 진행 |
| 4-B | `~같은 게임` 경로 | 참조 게임명 추출 및 DB 매칭 시도 |
| 5-B1 | similar + DB 존재 | DB 참조 게임 기반 유사 후보 검색 |
| 5-B2 | similar + DB 미존재(LLM) | LLM 프로파일 추정으로 대체 질의 생성 |
| 6 | 공통 합류 | 분기 경로를 공통 검색 입력으로 단일화 |
| 7 | 후보 검색 + 하드 필터 | 유사 후보 탐색 후 제외/필수 조건 필터링 |
| 8 | 점수 계산/재정렬 | 정합도/유사도/취향 신호 결합한 최종 점수 계산 |
| 9 | 추천 이유 생성 | 근거 요약, 추천 사유(reason), 한줄 요약 생성 |
| 10 | 최종 결과 출력 | 사용자 화면 카드/표 형태로 렌더링 |

### 3-2. 분기/합류 흐름(방향성)
- 메인 흐름: `1 -> 2 -> 3`
- 분기:
1. `3 -> 4-A -> 6`
2. `3 -> 4-B -> 5-B1 -> 6`
3. `3 -> 4-B -> 5-B2 -> 6`
- 합류 이후 공통: `6 -> 7 -> 8 -> 9 -> 10`

### 3-3. 단계 클릭 시 표시되는 상세 정보
각 단계 박스 클릭 시 아래 정보가 표시되도록 구현되어 있습니다.
1. INPUT
2. PROCESS
3. OUTPUT
4. 핵심 변수명/설명
5. 해당 단계 공식·가중치(있는 경우)
6. 왜 해당 비중인지 배경 설명

### 3-4. 단계별 핵심 변수(요약)
- 질의/파싱: `query`, `top_k`, `preferred_genres`, `excluded_genres_or_moods`, `must_have`, `soft_preferences`
- 분기: `mode`, `reference_hint`, `reference_game`, `similar_to_fallback`
- 검색/재랭킹: `similarity`, `query_alignment_score`, `preferred_genre_hits`, `soft_match_count`, `hidden_gem_score`, `recent_review_count`
- 출력: `results`, `reason_ko`, `one_liner_ko`

## 4) 공식·가중치·근거 (보고서 필수 섹션)

### 4-1. 질의 벡터 의도 보정
- 공식: `q_vec' = 0.8*q_vec + 0.2*bias_vec`
- 의도:
1. 원문 의미를 80% 유지해 질의 왜곡 방지
2. 취향 신호를 20%만 혼합해 모호 질의 분리력 강화

### 4-2. 일반 모드 최종 점수
- 공식:
`final_score = 0.34*alignment + 0.40*similarity + 0.12*genre_hits + 0.08*soft_match + 0.06*review_norm`
- 근거:
1. `similarity(0.40)`를 최대로 두어 전체 관련성 중심축 유지
2. `alignment(0.34)`로 질의 키워드 반영 여부를 강하게 보정
3. `genre_hits(0.12)`, `soft_match(0.08)`는 취향 미세 조정
4. `review_norm(0.06)`으로 리뷰 수 부족 후보 과대평가 방지

### 4-3. HiddenGem 모드 최종 점수
- 공식:
`final_score = 0.32*alignment + 0.30*hidden_gem + 0.24*similarity + 0.08*genre_hits + 0.06*soft_match`
- 근거:
1. HiddenGem 목적상 `hidden_gem(0.30)` 비중 확대
2. `similarity`는 0.24로 낮춰 인기작 편향 완화
3. `alignment(0.32)`를 유지해 질의 적합성 보장

### 4-4. HiddenGem 내부 점수
- 공식:
`hidden_gem = 0.6*long_tail + 0.3*quality + 0.1*engagement`
- 근거:
1. 롱테일 발굴(0.6)을 핵심 목표로 설정
2. 품질(0.3) 안전장치로 저품질 후보 억제
3. 참여도(0.1)는 장르 편향이 커 보조 신호만 반영

### 4-5. 다양성(MMR) 재선택
- 공식:
`mmr = (1-0.22)*relevance - 0.22*max_sim`
- 근거:
1. 관련성 78%를 우선 유지
2. 중복 후보 억제를 위해 다양성 22% 반영

### 4-6. fallback 설계 근거
- 트리거: `DB miss -> LLM profile inference`
- 근거: DB에 참조 게임이 없어도 `~같은 게임` 질의를 버리지 않고 대체 경로를 제공

### 5-3. 버전 전환 해석(무엇이/왜)
- v1 -> v2
1. 무엇: 파서 성공률/결과 비어있음 개선, 하드 제약 위반 증가
2. 왜: 파싱/리콜을 올리는 과정에서 제약 필터가 느슨해진 구간

- v2 -> v3
1. 무엇: 지표 거의 동일
2. 왜: 기능 추가보다 안정화/리팩터링

- v3 -> v4
1. 무엇: 지표 거의 동일
2. 왜: 대형 로직 변경 없이 유지

- v4 -> v5
1. 무엇: 하드 제약 위반 제거, 추천 실패 0
2. 왜: 제외/필수 조건 필터 순서/강도 보정 효과

- v5 -> v6
1. 무엇: non-empty 악화(1.0 -> 0.8333)
2. 왜: 과필터링으로 일부 질의 빈 결과

- v6 -> v7
1. 무엇: non-empty 회복, genre_hit 개선
2. 왜: 과필터 완화로 정밀도-재현율 균형 복구

- v7 -> v8
1. 무엇: pass 급락(1.0 -> 0.7375), parse_fail 증가(0 -> 20)
2. 왜: 평가셋 확장(12 -> 60) 및 난이도 상승으로 파서 취약점 노출

- v8 -> v9
1. 무엇: pass 일부 회복, genre_hit 1.0
2. 왜: 파싱 규칙/정규화 개선 반영

- v9 -> v10
1. 무엇: pass 추가 회복, hard_violation 0.0, reco_fail 0
2. 왜: 제약 필터 안정화 + 파이프라인 완성도 상승

### 5-4. 대시보드 상 요약 문구
- v1~v7: 기본 안정화 + 제약 준수/결과 반환 밸런스 조정
- v8: 평가셋 확장으로 파서 취약점 노출
- v9~v10: hard 케이스 개선 및 제약 위반 0 달성
- 한 줄 결론: v1~v7 개선, v8 파싱 회귀, v9~v10 추천 품질 안정 + 파싱 부분 회복

## 6) 보고서에 바로 넣을 수 있는 핵심 결론
- 본 모델은 정확도 축(`similarity + alignment`)을 중심으로 유지하고, 취향 보정(`genre_hits`, `soft_match`) 및 신뢰도 보정(`review_norm`)을 보조 가중치로 결합한 구조입니다.
- HiddenGem 모드에서는 롱테일 탐색 가중치를 의도적으로 확대해 인기 편향을 줄였고, MMR을 통해 상위 결과 중복을 제어했습니다.
- 버전 히스토리는 중반까지는 제약-반환 트레이드오프를 조정하는 과정이었고, v8의 평가셋 확장에서 파서 취약점이 노출된 뒤 v9~v10에서 추천 품질 안정화와 제약 위반 0 달성으로 수렴했습니다.
